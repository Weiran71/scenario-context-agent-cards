# 基于用户情景和 Context 的 Agent 卡片服务生成框架

## 详细技术报告母稿 v0.2（公开脱敏版）

> 本文是公开技术报告的详细母稿。文中的用户、事件、地点、字段值、规则参数和案例均为合成示例，不代表任何真实地图、商业推荐、导航产品或企业内部实现。公开代码是透明、可运行的最小基线，本文同时说明方法目标与当前基线的实现边界。

## 0. 阅读说明

这份报告回答的不是“如何写一条推荐文案”，而是一个更完整的问题：当 Agent 收到大量用户、环境、事件和地点 Context 时，如何判断此刻是否有值得提供的服务，并把判断转成一张可解释、可评测的卡片。

全文按照“问题 → 数据 → 中间推理 → 服务决策 → 卡片生成 → 评测 → 复现”的顺序组织。每个关键模块都包含五个部分：

1. 模块要解决的问题；
2. 输入和输出；
3. 具体执行逻辑；
4. 边界、失败分支和可追溯要求；
5. 一个紧跟其后的合成案例。

报告中有两条需要区分的链路：

- **数据集生产链路**：为了得到合理的评测样本，先选事实锚点，再构造与之匹配的 Context，形成完整 Case。
- **Case 运行链路**：拿到完整 Case 后，依次进行情景识别、需求翻译、候选处理、服务决策和卡片生成。

两条链路的顺序不同，但共享同一套中间契约和约束。

## 1. 摘要

主动服务型 Agent 的难点不是“能不能生成一段文案”，而是“在这一刻，是否有足够理由向这个用户提供一张卡片”。用户画像、时间、天气、位置、事件和地点特征共同构成了大量 Context，但这些 Context 不能被直接拼接成输出：有些信息与当前情景无关，有些信息只提供约束，有些信息需要和其他事实组合后才产生服务价值。

本文提出一套“Context → 情景 → 潜在需求与约束 → 候选与事实判断 → 服务决策 → 卡片生成 → 评测”的 Agent 卡片服务生成框架。框架支持两类卡片：事件提醒卡和 POI 推荐卡。事件提醒卡围绕一个当前有效的事件，判断是否值得在当前时机提醒；POI 推荐卡围绕用户当前的时空和特征，先形成潜在需求，再从候选地点中筛选和排序出 1～3 个地点。两类卡片共享 Context、服务决策和评测底座，但保留不同的候选逻辑和内容契约。

框架的核心设计有三点。第一，用可审计的需求记录承接 Context 到服务动作之间的推理，避免从字段直接跳到文案。第二，把 `serve` 和 `stay_silent` 都定义为正式输出，避免为了完成生成任务而强行出卡。第三，同时构造正向和负向 Case，并用统一 Rubric 评估相关性、价值、事实依据、表达和克制度。

公开实现使用透明、无依赖的确定性规则与完全合成数据，便于读者复现和替换为自己的检索、排序或生成组件。

## 2. 问题定义、目标与贡献

### 2.1 主动卡片服务与普通推荐的区别

普通推荐主要回答“用户可能喜欢什么”；主动卡片服务还要回答“现在是否值得打扰用户”。这增加了三个前置判断：当前情景是什么、用户在此情景下可能需要什么、系统是否拥有足够可靠且可承接的事实。

如果把所有 Context 直接交给生成模型，系统容易出现四类错误：

| 错误 | 具体表现 | 框架中的解法 |
|---|---|---|
| 相关性错误 | Context 存在，但与此刻无关，仍被写进文案 | 先形成情景和需求记录，区分证据、关系信号和约束 |
| 时机错误 | 内容有价值，但已过期、太远或不适合当前天气 | 在服务判断前执行事实有效性、距离和可行动窗口检查 |
| 服务错误 | 有兴趣不等于现在应该出卡，系统总是强行输出 | 将 `stay_silent` 定义为正式结果，并记录沉默原因 |
| 证据错误 | 文案听起来合理，却无法追溯来源 | 输出 `evidence`、`decision_reasons`，并做事实校验 |

### 2.2 目标

本框架的目标不是最大化出卡数量，而是在可追溯事实的基础上，稳定做到：

1. 该服务时能够服务；
2. 不该服务时能够沉默；
3. 服务内容与当前用户情景有关；
4. 内容来自输入事实，而不是生成模型的自由补全；
5. 每个中间判断都能被产品、算法和评测人员复核。

### 2.3 公开版本的贡献点

本文将以下做法组合成一个可运行的公开框架：

1. **需求翻译契约**：用 `need_record` 把多源 Context 转成情景、潜在需求、约束、证据和置信度。
2. **双路径卡片流程**：事件卡围绕 Event 事实锚点判断是否提醒；POI 卡先翻译需求，再处理候选地点。
3. **服务决策出口**：`serve` 与 `stay_silent` 都进入统一输出契约。
4. **正负向数据集**：同时验证“应该出什么”和“不应该出什么”。
5. **可解释评测**：用统一 Rubric 分开评估情景相关性、用户价值、事实可信度、表达质量和服务克制度。

### 3.2 各模块速览

| 模块 | 解决的问题 | 主要产出 | 下游使用 |
|---|---|---|---|
| Context 规范化 | 输入是否完整、可用、符合边界 | 规范化 Context、缺口和禁用项 | 情景识别 |
| 情景识别 | 当前到底发生了什么 | `situation` | 需求翻译 |
| 需求翻译 | 用户此刻可能需要什么、不能接受什么 | `need_record` | 候选、排序、服务决策、解释 |
| 候选处理 | 哪些事实或地点值得继续判断 | Event 判断结果或 POI 候选集 | 服务决策 |
| 服务决策 | 现在该不该出卡 | `serve` / `stay_silent` | 内容生成或沉默输出 |
| 内容生成 | 如何把判断转成卡片 | `card`、Action、Icon、理由 | 端上展示、内部评测 |
| 校验评测 | 输出是否可靠、可复现 | 校验结果、Rubric 分数 | 版本迭代 |

### 3.3 分层的必要性

情景识别负责“发生了什么”，需求翻译负责“可能需要什么”，服务决策负责“是否值得服务”，内容生成负责“怎么表达”。四个问题不能合并为一次自由生成，否则无法定位错误来源：是 Context 不足、情景理解错、候选不合适、服务判断错，还是文案表达不佳。

## 4. 数据模型与中间契约

### 4.1 Context 的角色分类

一个字段在推理中的作用通常属于以下三类之一：

| 角色 | 含义 | 示例 | 使用边界 |
|---|---|---|---|
| 事实证据 | 直接描述正在发生的事情 | Event 状态、POI 开放状态、天气 | 可支撑情景和最终文案 |
| 关系信号 | 描述用户与事情/地点的关联 | 偏好命中、关系度、常驻/到访状态 | 可影响价值和排序，不能单独证明行动意图 |
| 约束条件 | 限制时间、距离、天气或可用性 | 距离、当前时段、暴雨、关闭状态 | 用于过滤、降权或沉默 |

同一个字段不应被默认视为“越多越好”。例如偏好标签可以作为关系信号，但不能单独证明用户现在就要去某个地点；天气通常是约束条件，也可能影响副文案，但不能单独决定 Icon 或推荐主题。

### 4.2 统一 Case 结构

```json
{
  "case_id": "event_positive_00",
  "card_type": "event",
  "expected_decision": "serve",
  "context": {
    "user": {},
    "environment": {},
    "event": {}
  }
}
```

`expected_decision` 是数据集对 Case 的预期，不是模型运行结果。运行后才产生 `decision`、`need_record`、`card` 和 `decision_reasons`，这样可以避免把输入标注和生成结果混在一起。

### 4.3 `need_record` 结构

公开基线中的需求记录包含五个部分：

```json
{
  "situation": "晚间，用户位于星河城区，面对一个周末市集事件",
  "need": "判断周末市集是否值得在当前时机提醒",
  "constraints": [
    "事实必须在当前时间有效",
    "不使用未提供的行程或订单信息",
    "优先当前可达且距离合理的内容"
  ],
  "evidence": [
    "时间处于晚间",
    "当前天气为晴朗",
    "用户属于常驻城市",
    "事件状态为active"
  ],
  "confidence": 0.85
}
```

字段含义和约束如下：

| 字段 | 具体定义 | 不能做什么 |
|---|---|---|
| `situation` | 对当前时空、用户关系和事实状态的简洁概括 | 不能添加未给出的用户计划 |
| `need` | 当前需要判断或满足的潜在需求 | 不能直接等同于“用户一定想去” |
| `constraints` | 时间、距离、可用性、数据边界等限制 | 不能把推测写成事实 |
| `evidence` | 真正支撑判断的输入字段或组合 | 不能列与结论无关的字段凑数量 |
| `confidence` | 需求翻译的可信程度 | 不等同于最终出卡概率 |

### 4.4 需求记录的下游作用

需求记录是模块之间的中间契约，而不是面向用户的文案：

1. 候选检索使用其中的空间、时间和主题约束；
2. 排序使用其中的关系信号和证据；
3. 服务判断检查候选是否满足关键约束；
4. 内容生成只能使用有证据支撑的需求；
5. 评测人员可以沿 `evidence` 回看为什么形成该情景。

> **案例：从 Context 到需求记录**
>
> 输入：用户处于常驻城市，当前上午，天气晴朗，附近 1.3 公里有一个状态为 active 的周末市集事件，关系度为 0.72。
>
> 翻译：情景是“上午、附近、当前有效的周末市集”；需求是“判断是否值得在此刻提醒”；约束是“事件必须有效、距离合理、不得依赖不存在的行程”；证据来自时间、天气、常驻状态、事件状态、距离和关系度。
>
> 作用：事件路径据此决定是否出卡；如果事件状态变为 inactive 或距离超过边界，后续服务判断可以沉默，而不是继续生成原来的文案。

## 5. 两条链路：数据集生产与 Case 运行

### 5.1 数据集生产链路

```text
确定卡片类型与覆盖目标
          ↓
选择事实锚点
  ┌───────┴────────┐
  │事件卡：Event    │ POI卡：用户情景/候选池
  └───────┬────────┘
          ↓
构造匹配的用户、时间、位置、天气和候选数据
          ↓
形成完整 Case，并标注 expected_decision
          ↓
运行生成链路
          ↓
自动校验 + 人工/模型抽样复核
          ↓
修正错误、检查分布、输出数据集
```

事件卡生产必须先选 Event，再构造与 Event 在时间、位置、用户关系上相容的 Context；否则容易出现“事件在晚上发生，用户却处于无法解释的时间状态”等离谱样本。POI 卡生产则先定义当前用户情景和需求边界，再构造候选池，避免先挑地点再倒推理由。

### 5.2 Case 运行链路

```text
读取完整 Case
      ↓
Context 规范化
      ↓
情景识别
      ↓
need_record
      ↓
候选处理 / Event 判断
      ↓
serve 或 stay_silent
      ├── stay_silent：输出沉默原因
      └── serve：生成对应卡片字段
                         ↓
                    校验与评测
```

### 5.3 两条链路的关系

数据集生产是“构造合理输入”，运行链路是“处理已构造输入”。生产时可以利用对 Event 或候选池的全局了解，但运行时只能使用 Case 里提供的事实。这个区分可以防止生成器在运行阶段偷偷使用数据集外的信息。

## 6. 通用模块详解

### 6.1 Context 规范化

#### 解决的问题

先确认输入能不能被使用，而不是让后续模块在缺字段、类型错误或禁用依赖上继续推理。

#### 输入与输出

输入是原始 Case；输出是规范化 Context、缺失字段、禁止依赖和需要降级的标记。

#### 执行逻辑

1. 检查 `card_type` 是否为 `event` 或 `poi`；
2. 检查用户和环境基本字段是否存在；
3. 对时间、距离、状态等数值和枚举做类型转换；
4. 标记不可使用的计划、订单、导航目的地等字段；
5. 对缺少关键事实的 Case 提前降级或转为负向样本。

#### 边界与证据

规范化不负责补造事实。缺失 Event 状态不能默认当作 active；缺少 POI 开放状态不能默认当作 open。可以在数据集生产阶段明确 Mock，但运行阶段必须把 Mock 值视为 Case 的显式输入。

> **案例：缺少状态的 Event**
>
> 如果 Event 只有“今晚有音乐会”，没有状态和距离，系统不能直接生成提醒。正确处理是标记事实缺口，或在数据集生产阶段补齐合成的 `status`、`distance_km` 和 `relevance` 后再运行。

### 6.2 情景识别

#### 解决的问题

把离散字段变成一句能被后续模块使用的当前情景，而不是把字段原样拼接。

#### 执行逻辑

1. 根据当地小时映射清晨、上午、午间、下午、晚间、深夜；
2. 抽取天气和空间关系；
3. 根据 `local_status` 识别常驻城市或到访城市关系；
4. 事件卡加入 Event 主题和状态；
5. POI 卡描述“此刻需要附近可去的地点”，并补充偏好证据。

#### 不能做什么

情景识别不推断用户明确计划，不把“有偏好”写成“用户现在一定要行动”，也不把天气直接写成服务结论。

> **案例：偏好不是计划**
>
> 用户偏好标签为“咖啡”，只能形成“可能适合咖啡相关去处”的情景信号，不能写成“用户正在寻找咖啡店”。后者需要当前情景或显式行为事实支持。

### 6.3 需求与约束翻译

#### 解决的问题

把情景转成后续搜索、过滤、排序和决策可以执行的记录。

#### 执行逻辑

需求记录必须回答四个问题：

1. 当前情景是什么；
2. 用户可能需要什么；
3. 结果必须满足哪些限制；
4. 这些判断分别依据哪些事实。

#### 失败分支

如果没有足够证据形成需求，不应使用强断言。可以降低置信度、输出观察型需求，或直接进入 `stay_silent`。

### 6.4 服务决策

#### 解决的问题

在内容生成前判断是否有足够服务价值。

#### 统一决策树

```text
事实是否当前有效？
      │否 → stay_silent
      │是
      ▼
用户关系和当前价值是否足够？
      │否 → stay_silent
      │是
      ▼
时间、距离、可用性约束是否满足？
      │否 → stay_silent
      │是
      ▼
是否有可承接的 Event / POI？
      │否 → stay_silent
      │是
      ▼
serve → 进入内容生成
```

#### 设计要求

`stay_silent` 必须带有可复核原因，例如“事件不是当前有效状态”“事件距离超过服务边界”“没有候选地点同时满足距离、可用性和关系条件”。沉默不是空结果，也不是生成失败，而是主动服务系统的正式能力。

### 6.5 内容生成

内容生成只在 `serve` 后执行。它应该把已经成立的情景和事实压缩成用户能理解的卡片，而不是重新决定是否服务。用户可见字段和内部字段分离：主文案、副文案、Action 和 POI 名称面向用户或端上承接；主题、推荐理由、证据和决策原因面向产品、算法和评测。

### 6.6 校验与评测

校验至少分为五层：

1. **结构校验**：JSON 可解析、字段存在、枚举合法；
2. **决策校验**：实际决策与预期决策一致；
3. **事实校验**：文案、Action、POI 和 Icon 能追溯到输入；
4. **边界校验**：数量、距离、禁用类型、字数和标点符合规则；
5. **语义评测**：用 Taste/Rubric 判断相关性、价值、可信度、表达和克制度。

公开基线的自动验证器只覆盖其中一部分，具体差异见第 11 节。

## 7. 事件提醒卡的完整方法

### 7.1 定位与事实锚点

事件提醒卡回答：“这个当前有效的事件，现在是否值得提醒给这个用户？”它以一个 Event 为事实锚点，再构造或读取与该 Event 相容的用户和环境 Context。

Event 至少需要包含：主题、状态、距离、关系度、事实描述和可执行动作。公开基线使用 `theme`、`status`、`distance_km`、`relevance`、`fact_line`、`action` 和 `icon_tag`。

事件卡不能依赖用户未提供的行程、订单、导航目的地或足迹；地点榜单类内容不作为事件事实。`TOPLIST_POI` 这类地点发现类型应进入 POI 推荐路径，而不是事件提醒路径。

> **案例：为什么 Event 是生产起点**
>
> 生产一条“周末市集”提醒时，先选定 Event 的主题、时间事实、地点和当前状态，再构造一个距离合理、偏好关系成立的用户 Context。不能先随便生成一个用户画像，再寻找任何能套上的事件。

### 7.2 三条情景构造路径与一个承接校验

三条路径是数据集生产时发现候选情景的不同入口，不是线上运行时的三个模型分支；每条 Case 记录一条主路径即可。

```text
PATH-1：一级场景向下独立构思 ─┐
PATH-2：旧二级场景扩展       ─┼─→ 候选提醒情景 → Event 事实复核
PATH-3：Context 自下而上组合 ─┘                         │
                                                       ▼
                                   PATH-4：Action 承接校验
```

| 路径 | 起点 | 执行方法 | 价值 | 主要风险与解法 |
|---|---|---|---|---|
| PATH-1 | 一级生活领域 | 从领域中独立思考当前可能发生的机会、变化或麻烦，再回到 Event 池验证 | 不被旧二级场景穷尽性限制 | 容易停留在空洞主题；必须落到时间、位置、Event 和可行动变化 |
| PATH-2 | 旧二级场景 | 把旧场景只当灵感种子，重新用当前 Context 和 Event 验证 | 保留过去有价值的想法，同时修正旧依赖 | 不得照搬行程、订单、导航状态等已废弃依赖 |
| PATH-3 | 可用 Context | 找到“用户相关性 × 当前变化 × 还能行动”的交集，再归到一级场景 | 发现旧场景库没有覆盖的合理组合 | 不能把相关性当因果；缺少关键事实时应条件化或沉默 |
| PATH-4 | 已成立的提醒 | 检查真实 Action 是否能承接，地点类 Action 绑定同源 POI | 保证卡片能完成后续动作 | 不能从按钮反向造情景，只能作为成立后的承接校验 |

> **案例：同一个主题可以由不同路径发现**
>
> “雨天适合室内活动”可以由 PATH-1 从休闲领域独立构思；也可以由 PATH-2 从旧的“高温时选室内”场景重新验证；还可以由 PATH-3 从雨天、附近室内 Event 和用户偏好组合得到。三者的输出可能相似，但生产轨迹不同，不能为了分布好看而事后改标。

### 7.3 Event 事实复核

情景候选产生后，必须回到 Event 数据复核：

1. Event 是否存在且属于允许类型；
2. 状态是否当前有效；
3. 事实描述是否包含可解释的时间和地点；
4. 距离是否在服务边界内；
5. 关系度是否足以说明对当前用户有价值；
6. 是否有真实可执行的 Action。

公开基线的服务门槛为：`status == active`、`distance_km <= 8`、`relevance >= 0.6`。这些是可替换的演示参数，不是所有产品必须使用的固定值。

### 7.4 Event 与 Context 的匹配构造

在数据集生产阶段，先选 Event，再构造匹配 Context。匹配至少包括：

| 维度 | 匹配要求 | 反例 |
|---|---|---|
| 时间 | 当前小时与 Event 的事实窗口有合理关系 | Event 只在白天，Case 却设为深夜仍强推 |
| 空间 | 用户所在城区与 Event 距离一致 | 文案说“就在附近”，距离却超过服务边界 |
| 用户关系 | 偏好、常驻/到访状态或关系度能支撑价值 | 完全无关系却标为高相关 |
| 天气 | 户外/室内属性与天气不明显冲突 | 暴雨下直接推荐无保护的户外活动 |
| Action | 事件事实能由动作承接 | 事件卡输出一个与事件无关的按钮 |

如果匹配条件不足，不能通过在运行阶段隐式补字段解决；应在数据集生产阶段修正 Context，或将该 Case 改为负向。

### 7.5 情景与需求记录

事件卡的 `need_record` 重点是“是否值得在当前时机提醒”，而不是“用户一定会去”。

```text
事件事实：当前有效的周末市集
        ↓
情景：上午、用户在附近、面对一个当前有效的周末市集事件
        ↓
需求：判断此刻提醒是否能降低用户发现和决策成本
        ↓
约束：事实有效、距离合理、关系足够、不使用不存在的计划信息
```

### 7.6 服务决策与沉默原因

公开基线按以下顺序判断：

1. 状态不是 `active`：沉默；
2. 距离大于 8 公里：沉默；
3. 关系度低于 0.6：沉默；
4. 没有任何失败原因：服务。

> **案例：过期事件不应出卡**
>
> Event 主题是“户外演出”，距离 1.5 公里，关系度 0.86，但状态为 `expired`。尽管距离和关系都成立，事实已经失效，结果必须是 `stay_silent`，并记录“事件不是当前有效状态”。

### 7.7 事件卡内容生成

#### 主文案

主文案表达“与用户的关系 + 当前价值 + 具体事情”，最多 16 个中文字符，结尾不使用句号或其他标点。它不能只是 Event 名称的机械复述，也不能固定追加“可以看详情”“可以看路线”等尾句。

生产时应先写出完整语义，再压缩到卡片长度：

```text
用户关系 / 当前情景 + 能带来的价值 + 具体事件
```

#### 副文案

副文案承接结构化事实，优先使用 Event 的事实描述、时间、地点等可靠字段。若 Action 已明确指向某个 POI 详情，副文案不再重复 ETA 类信息；副文案不是营销口号，也不能添加输入中不存在的事实。

#### Action

Action 必须是用户视角的可执行动作，长度为 2～4 个中文字符，避免信息标签化。地点类 Action 必须绑定可追溯的 POI 名称和 ID。一个 Case 只输出一个最自然的 Action；不为了展示能力堆多个按钮。

#### Icon

Icon 主要依据事件和关联 POI 类型选择，天气只能作为辅助信号，不能成为主要依据。标签同时输出英文和中文，例如 `{"en":"market","zh":"市集"}`。

> **案例：事件卡完整生成**
>
> 输入：用户为常驻城市用户，当前上午，天气晴朗；Event 为“周末市集”，状态 active，距离 1.3 公里，关系度 0.72，事实为“今天 10:00-18:00，星河城区有周末市集”。
>
> 需求记录：上午、附近、当前有效的市集，适合判断是否降低用户发现成本。
>
> 决策：`serve`。
>
> 主文案：“周末有去处 正好离你近”。
>
> 副文案：“今天10:00-18:00，星河城区有周末市集”。
>
> Action：“去看看”。
>
> Icon：`market / 市集`。

### 7.8 事件卡校验清单

| 检查项 | 通过标准 | 失败处理 |
|---|---|---|
| Event 类型 | 不是禁用地点榜单类类型 | 删除或换回允许 Event |
| 当前有效性 | 状态和事实窗口支持当前服务 | 改为沉默或修正生产输入 |
| 用户关系 | 有偏好、关系度或情景证据 | 降权、沉默或重构 Case |
| Action | 一个用户可执行动作，能承接事件 | 换成更自然且在能力列表内的动作 |
| Icon | 事件/POI 类型匹配，中英双语 | 重新映射 |
| 文案 | 主文案长度、结尾、事实和语气通过 | 重写主/副文案 |

## 8. POI 推荐卡的完整方法

### 8.1 定位

POI 推荐卡回答：“在用户此刻的时空和特征下，哪些附近地点值得推荐？”它不是脱离当前情景的兴趣推荐，也没有 Action 按钮；最终推荐的 POI 本身就是可点击对象。

输入包括用户五维特征、常驻/到访状态、当前位置所在城区、时间、天气和 POI 候选池。每个 POI 至少需要 ID、名称、距离、开放状态、标签、Summary 主题和卡片主题。

### 8.2 Context 到潜在需求

POI 卡不能先看地点再寻找理由。正确顺序是：

```text
用户 + 环境 Context
          ↓
当前情景
          ↓
潜在需求与约束
          ↓
搜索/过滤条件
          ↓
候选 POI
```

需求记录要把模糊情景翻译为可执行条件：

- 距离边界决定候选范围；
- 天气决定室内、户外或低暴露约束；
- 用户偏好和 POI Summary 决定主题匹配；
- 时段和开放状态决定地点是否仍有行动价值。

> **案例：先形成需求再选地点**
>
> 输入：用户偏好“户外、轻松活动”，当前下午，天气晴朗，位于星河城区。
>
> 需求记录：寻找附近、当前可去、决策成本低的户外活动；约束是地点要开放、距离合理。
>
> 后续：先排除 7 公里外或已关闭地点，再在剩余候选中优先保留 Summary 主题与“轻松活动”一致的地点。不能先挑一个最热门地点，再把它解释成“轻松活动”。

### 8.3 候选池建立：距离优先

候选池的第一原则是“此刻可达”。公开基线先检查距离和开放状态：距离超过 5 公里或状态不是 `open` 的地点不进入有效候选。真实系统可以按城市、交通方式、时段和用户状态动态调整公里边界，但顺序不变：先保证空间可达，再比较兴趣和主题匹配。

候选池不是最终推荐结果。它保留多个候选，供后续结合 Summary、标签、关系和主题一致性进行精排。

### 8.4 粗排：结构化字段与 Summary 双路生效

粗排同时使用两路信息：

1. **结构化字段**：距离、开放状态、兴趣标签、消费区间、热度等稳定事实；
2. **Summary**：对地点特色和用户关系的概括，用于识别“为什么适合当前用户”。

公开基线评分示例：

```text
score = distance_score × 0.45
      + preference_overlap × 0.35
      + summary_match × 0.20
```

`summary_match` 在基线中用 `summary_theme` 是否命中 POI 标签或用户偏好表示。真实系统可以换成更丰富的语义匹配，但不能把 Summary 推迟到最终理由生成阶段才使用。

> **案例：Summary 让候选被降权**
>
> 两个地点距离都为 1.5 公里，也都带有“户外”标签。地点 A 的 Summary 主题是“亲子轻松活动”，地点 B 的 Summary 主题是“高强度攀岩”。如果当前用户偏好“轻松活动”，A 的 Summary 与需求一致，B 虽然标签相同，也应被降权或淘汰。只看一个标签无法得到这个判断。

### 8.5 精排与数量决策

精排在有效候选中综合距离、标签重合、Summary 主题匹配和主题一致性，最终选择 1～3 个 POI。

| 数量 | 适用条件 | 不适用情况 |
|---|---|---|
| 1 个 | 一个地点与需求高度匹配，其他候选明显弱 | 为了凑数量并列无关地点 |
| 2 个 | 同一主题下存在两个可比较选择 | 两个地点主题和用户价值不同 |
| 3 个 | 同一主题下有多个质量接近、距离合理的地点 | 候选质量明显递减或只是为了填满卡片 |

公开基线按分数降序最多取三个候选，最高分低于 0.42 时沉默。真实排序模型可以替换评分函数，但必须保留：最终 POI 来自候选池、数量不超过 3、没有足够匹配度时不出卡。

### 8.6 主题一致性

多个 POI 最好覆盖一个相似主题。主题可以来自 POI 的结构化主题或 Summary，但必须能解释为什么这些地点被放在一起。当前公开基线直接取分数最高的最多三个候选，未单独实现主题一致性过滤；因此“主题一致性”在报告中是方法要求，在基线中是待增强项。

### 8.7 POI 卡内容生成

#### 主题

主题是内部字段，用于说明这组地点为什么被放在一起，不直接展示给用户。

#### 主文案

主文案表达“这个用户此刻为什么值得去 + 具体去做什么”，控制在 12～16 个中文字符，最多不超过 16 个字符；中间允许有空格，结尾不使用标点。不能使用冒犯用户的“少花点”等暗示，也不能对同一类地点反复套用固定句式。

#### 副文案

副文案提供一行辅助事实，不使用 ETA 类信息作为 POI 卡公共副文案的默认内容，因为具体 ETA 在单个 POI 点位上承接。副文案必须来源于 POI 的结构化字段或 Summary，例如地点特色、适合人群、主题组合或可验证的营业信息；没有可靠事实时可以不出副文案。

#### 推荐理由

推荐理由是内部字段，不是 C 端文案。它需要说明距离、偏好命中、Summary 主题、结构化特征和主题一致性，但应保持精简，避免写成无法复核的大段解释。

#### 图片标签

图片标签按“二级 Tag > 一级分类”选择：

1. 多个 POI 有共同且合适的二级 Tag，使用二级 Tag；
2. 二级 Tag 无法共用，但有共同且合适的一级分类，使用一级分类；
3. 一级分类也不合适，输出“未找到合适标签”标识；
4. 不使用全局通用兜底替代真实匹配。

> **案例：POI 卡完整生成**
>
> 用户在常驻城市，当前下午，偏好“户外、轻松活动”；候选中有三个地点均在 3 公里内、处于开放状态，Summary 分别强调“城市绿地散步”“轻松骑行”“亲子户外”。
>
> 内部主题：“附近轻松户外”。
>
> 最终 POI：候选池中的三个 POI ID 和名称。
>
> 主文案：“附近有几处轻松户外去处”。
>
> 副文案：“3公里内，适合下午放松走走”。
>
> 推荐理由：距离均在候选边界内；命中“户外/轻松活动”偏好；Summary 都指向低强度户外；三个地点主题一致，适合并列展示。

### 8.8 POI 卡沉默逻辑

以下任一情况成立时，优先沉默：

- 候选池为空；
- 所有候选距离过远；
- 所有候选不可用；
- 候选与当前用户关系不足；
- 最高分低于服务门槛；
- 选出的多个 POI 无法形成可解释主题。

> **案例：有兴趣标签也不一定出卡**
>
> 用户偏好“阅读”，候选地点都带有“阅读”标签，但全部距离超过服务边界。此时应输出 `stay_silent`，而不是因为标签命中就推荐远处地点。

### 8.9 POI 卡校验清单

| 检查项 | 通过标准 | 失败处理 |
|---|---|---|
| 候选来源 | 最终 POI 必须来自候选池 | 删除池外对象并重排 |
| 数量 | 1～3 个 | 重新做数量决策 |
| 距离和状态 | 满足当前边界且开放 | 过滤或沉默 |
| Summary 使用 | 候选/排序/理由有可追溯作用 | 重新检查匹配逻辑 |
| 主题 | 多 POI 能解释为同一主题 | 减少数量或沉默 |
| 图片标签 | 二级 Tag 优先，其次一级分类 | 输出未找到合适标签 |
| 文案 | 12～16 字、无结尾标点、非模板化 | 重写主/副文案 |

## 9. 服务决策与内容生成的关系

### 9.1 先决策，后生成

内容生成不应重新决定是否服务。它的输入应包含：

- 已通过门槛的情景和需求记录；
- 已确认的 Event 或最终 POI；
- 可使用的事实证据；
- 对应卡片的输出契约和表达约束。

如果生成阶段发现没有可靠的事实，正确动作是返回缺口或沉默，而不是编造补齐。

### 9.2 用户字段与内部字段分离

```text
用户可见：主文案 / 副文案 / Action / POI名称
                    │
内部可审计：主题 / need_record / evidence / reasons / 评测分数
```

这种分离可以同时满足两种需求：用户看到简洁自然的内容；产品和算法能够理解为什么选择这张卡、为什么没有选择其他候选。

## 10. 正向与负向测评数据集

### 10.1 Case 最小组成

| 字段 | 说明 |
|---|---|
| `case_id` | 唯一标识 |
| `card_type` | `event` 或 `poi` |
| `context` | 用户、环境、Event 或候选 POI |
| `expected_decision` | 预期 `serve` 或 `stay_silent` |
| `scenario_label` | 合成情景标签，用于分布检查 |

### 10.2 正向 Case

正向 Case 验证该出卡时是否能出对：事实有效、关系成立、时机和距离合理、存在可承接内容。事件卡必须围绕允许的 Event 类型；POI 卡必须存在至少一个满足距离、状态和关系的候选。

### 10.3 负向 Case

负向 Case 验证系统是否克制。可覆盖：

| 负向类型 | 事件卡示例 | POI 卡示例 |
|---|---|---|
| 事实失效 | Event 已过期 | 候选全部 closed |
| 距离过远 | Event 超过服务边界 | 所有候选超过距离边界 |
| 关系不足 | relevance 低 | 标签和 Summary 均不匹配 |
| 时机不合适 | 事件窗口与当前时段冲突 | 地点在当前时段不可行动 |
| 承接缺失 | 没有可靠 Action | 没有可解释的最终候选 |

负向集不需要依赖另一张卡片承接。例如 POI 卡的负向 Case 应直接说明“当前没有值得推荐的地点”，不能把它设计成“那就改出一张事件卡”。

### 10.4 分布控制

数据集不追求所有排列组合，而是覆盖能改变服务决策或内容选择的变化：

- 不同时间段；
- 不同天气；
- 常驻/到访状态；
- 不同用户偏好组合；
- 不同 Event 类型和 POI 主题；
- 不同距离分布；
- 有特殊日期与普通日期；
- 单 POI 与多 POI；
- 正向与负向比例。

特殊日期可以出现，但不能让数据集几乎每条都有特殊日期；真实分布中大量普通日期必须被保留。数据生产后应统计空值、非空值、类型和主题分布，防止某个节日、天气或模板垄断样本。

### 10.5 生产后的自查

每批数据至少做一次以下自查：

1. 结构：每行 JSON 可解析，字段和类型正确；
2. 来源：文案、理由、POI 和 Icon 能回查到输入；
3. 决策：实际结果与 `expected_decision` 一致；
4. 边界：禁用 Event 类型、池外 POI、超量 POI、无效 Action 被剔除；
5. 表达：主文案长度、结尾标点、数字格式、模板重复和冒犯性表达；
6. 分布：时间、天气、特殊日期、用户状态、主题和负向类型不过度集中；
7. 抽样：随机查看若干 Case，从 Context 读到最终卡片，确认推理链不跳步。

## 11. Taste 与 Rubric

### 11.1 Taste 的作用

Taste 是“什么样的服务才值得被认为是好服务”的产品判断，不等同于字段规则。它约束输出应该有真实关系、即时价值、事实依据、自然表达和适度克制。

### 11.2 Rubric 的作用

Rubric 把 Taste 转成可执行的 0～2 分评测。每个维度同时包含评估定义、两类卡片的细则和参考案例。评分采用“关键条件满足度”的整体判断，不把所有描述性条件机械地写成必须全部同时出现的硬门槛。

### 11.3 五个统一维度

| 维度 | 评估什么 | 事件卡重点 | POI 卡重点 |
|---|---|---|---|
| D1 相关性与情景贴合 | 是否回应当前情景、用户关系和此刻需求 | Event 是否值得现在提醒 | POI 是否适合当前时空和用户 |
| D2 用户价值 | 是否提供具体、清晰、值得行动的价值 | 提醒是否降低发现/决策成本 | 推荐是否降低找地点成本 |
| D3 事实依据与可信度 | 是否能追溯到输入，是否虚构 | Event、时间、地点、Action、Icon | POI、距离、Summary、主题、图片标签 |
| D4 表达自然度与可读性 | 是否简洁、自然、符合卡片语气 | 主副文案、按钮和 Icon 表达 | 主副文案、主题和多 POI 表达 |
| D5 服务克制度与选择质量 | 是否该出才出、该沉默时沉默 | Event 门槛和沉默原因 | 候选质量、数量和主题一致性 |

### 11.4 分数解释

- **2 分**：关键判断成立，内容与事实和情景高度一致，没有明显越界或表达问题。
- **1 分**：主要方向成立，但存在一处可感知的不足，例如价值不够具体、理由不够充分、表达略模板化或候选选择仍可优化。
- **0 分**：关键判断失败，例如当前不该出却出卡、事实无法支撑、推荐明显脱离情景或内容无法使用。

评分结果要保留维度分数和评语，不能只保留一个总分。这样可以区分“情景判断正确但文案差”和“文案通顺但本来不该出卡”。

## 12. 公开基线实现与方法目标的差异

公开仓库的实现是透明、确定性的最小基线。报告方法可以扩展，但不能把未实现的能力写成已经完成。

| 方法要求 | 当前公开基线 | 解释 |
|---|---|---|
| Summary 参与候选和排序 | 用 `summary_theme` 二值命中加分 | 证明 Summary 在粗排阶段生效，但不是完整语义匹配 |
| 多 POI 主题一致性 | 直接按分数和距离取前 3 | 主题一致性是方法要求，基线尚未独立过滤 |
| Event 当前窗口判断 | 检查 `status`、距离和关系度 | 未解析 Event 的详细时间窗口 |
| 天气和时间参与 POI 排序 | 主要影响 `need_record` | 当前 POI 分数未直接使用天气/时间 |
| 事实和证据校验 | 输出理由和结构，验证器不证明语义来源 | 语义需人工或模型 Rubric 评审 |
| PATH-1/2/3/4 轨迹 | 生产方法中定义，公开 40 条基线未持久化完整轨迹字段 | 后续可增加 `construction_trace` |
| Schema 覆盖 | Schema 声明核心字段 | `source`、`expected_decision`、`candidate_pool`、`selected_pois` 属扩展字段 |
| 自动验证 | JSON、核心字段、枚举、决策一致性、沉默卡片为空、重复 ID、禁词 | 不检查语义相关性、Summary 质量和文案自然度 |

这组差异不是缺陷掩盖，而是公开版本的边界声明。先用透明规则跑通完整链路，再逐步替换单个模块，比用一个不可解释的黑盒模型掩盖流程缺口更适合公开研究原型。

## 13. Demo 与复现

### 13.1 Demo 交互

公开 Demo 是一个不连接商业 API 的静态浏览器应用。用户可以：

1. 选择事件提醒卡或 POI 推荐卡；
2. 选择一个公开合成 Case；
3. 调整当地时间、天气和偏好标签；
4. 点击“运行 Case”；
5. 查看输入 Context、情景与潜在需求、候选、服务决策、最终卡片和内部判断依据。

运行状态会显示最近运行的 Case 和时间，便于确认交互已经生效。Demo 的目的不是模拟真实地图检索，而是让中间推理契约可见。

### 13.2 代码入口

```text
pipeline/engine.py       需求翻译、事件卡和 POI 卡基线逻辑
pipeline/run_examples.py 批量运行公开 Case
schemas/                 Context 与卡片输出结构
data/                    合成正负向 Case
validators/              结构与公开边界校验
hf_space/index.html      无服务端依赖的浏览器 Demo
```

### 13.3 最小复现命令

```bash
python3 pipeline/run_examples.py
python3 validators/validate_outputs.py examples/generated_outputs.jsonl
python3 -m unittest discover -s tests -v
```

预期结果是：两类卡片均能运行，正向 Case 返回 `serve`，负向 Case 返回 `stay_silent`，并通过公开边界检查。

## 14. 局限、风险与后续工作

### 14.1 当前局限

第一，公开数据为合成数据，不能代表真实用户分布、真实地点质量或线上点击效果。第二，公开基线使用透明规则，权重和门槛用于展示流程，并非经过大规模线上校准的生产参数。第三，当前 Rubric 需要人工或模型评审来完成语义判断，自动校验只能覆盖结构和部分硬约束。第四，部分方法要求已经写入报告，但尚未在最小代码中完整实现，例如复杂 Summary 语义匹配、主题一致性过滤和完整构造轨迹。

### 14.2 使用风险与解法

| 风险 | 原因 | 解法 |
|---|---|---|
| 隐私风险 | 真实画像和行为数据被直接用于生成 | 先完成授权、脱敏、最小化和访问控制 |
| 事实风险 | 生成文案超出输入事实 | 强制 evidence 回查和事实校验 |
| 过度打扰 | 把兴趣当成当前需求，或取消沉默出口 | 保留 `stay_silent`，建立负向数据集 |
| 数据偏差 | 某个节日、主题或天气占满样本 | 做分布统计和批次级抽样复核 |
| 规则误用 | 将演示门槛当成生产参数 | 线上重新校准，并在文档中标注版本 |

### 14.3 可扩展方向

后续可以在不改变总体顺序的前提下替换模块：

1. 用真实检索系统替换候选池生成；
2. 用学习排序替换透明评分函数；
3. 用语言模型替换内容生成；
4. 用自动评测器辅助执行 Rubric；
5. 将用户反馈接入 Case 采样、负向挖掘和规则迭代；
6. 为数据生产增加 `construction_trace`，记录路径、关键证据和修正历史。

无论如何扩展，都应保留“先形成情景和需求、再处理候选、再做服务决策、最后生成内容”的可审计顺序。

---

## 15. 结论

Agent 卡片服务的核心不是让模型写出更多文案，而是让系统在复杂 Context 中做出可解释的服务判断。本文框架用需求记录把 Context 和卡片之间的推理显式化，用 `serve` / `stay_silent` 统一表达服务与克制，用事件卡和 POI 卡两条不同路径承接不同事实结构，并通过正向、负向 Case 和 Rubric 把结果变成可重复评测的对象。

这种方法的可迁移性来自流程契约，而不是某个城市、某个地点或某组固定规则：只要新的 Agent 服务也需要理解当前情景、判断是否值得服务、选择可承接内容并生成用户卡片，就可以复用同一套分层思路，再替换具体 Context、候选和内容规则。

### A.1 事件提醒卡正向案例

```text
输入 Context
  用户：常驻城市；偏好=户外、轻松活动
  环境：星河城区；09:00；晴朗

  上午，用户位于附近，面对当前有效的周末市集事件

需求记录
  需求：判断周末市集是否值得在当前时机提醒
  约束：事实有效、距离合理、不使用不存在的行程/订单
  证据：时间、天气、常驻状态、Event 状态、距离、关系度

服务决策
  status=active ✓   distance=1.3≤8 ✓   relevance=.72≥.6 ✓
  结果：serve

卡片
  主文案：周末有去处 正好离你近
  副文案：今天10:00-18:00，星河城区有周末市集
  Action：去看看
  Icon：market / 市集
```

### A.2 POI 推荐卡负向案例

```text
输入 Context
  用户：偏好=阅读
  环境：南湖城区；16:00；阴天
  候选：两个地点均为 open，但距离分别为 12km、15km

情景与需求
  需求：寻找当前可达、低决策成本的附近去处
  约束：距离≤5km、地点开放、与用户关系足够

候选处理
  两个候选均超过距离边界 → 有效候选为空

服务决策
  结果：stay_silent
  原因：没有候选地点同时满足距离、可用性和关系条件
  卡片：null
```
