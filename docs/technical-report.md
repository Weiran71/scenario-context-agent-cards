# 基于用户情景和 Context 的 Agent 卡片服务生成框架

## 技术报告母稿（公开脱敏版）

> 本文是公开技术报告的母稿。文中的用户、事件、地点、字段值、规则参数和案例均为合成示例，不代表任何真实地图、商业推荐或导航产品。本文讨论的是一套可复现的方法框架，而不是某个线上系统的实现披露。

## 摘要

主动服务型 Agent 的难点不是“能不能生成一段文案”，而是“在这一刻，是否有足够理由向这个用户提供一张卡片”。用户画像、时间、天气、位置、事件和地点特征共同构成了大量 Context，但这些 Context 不能被直接拼接成输出：有些信息与当前情景无关，有些信息只提供约束，有些信息需要和其他事实组合后才产生服务价值。

本文提出一套“Context → 情景 → 潜在需求与约束 → 候选与事实判断 → 服务决策 → 卡片生成 → 评测”的 Agent 卡片服务生成框架。框架支持两类卡片：事件提醒卡和 POI 推荐卡。事件提醒卡围绕一个当前有效的事件，判断是否值得在当前时机提醒；POI 推荐卡围绕用户当前的时空和特征，先形成潜在需求，再从候选地点中筛选和排序出 1～3 个地点。两类卡片共享 Context、服务决策和评测底座，但保留不同的候选逻辑和内容契约。

框架的三个核心设计是：第一，用可审计的需求记录承接 Context 到服务动作之间的推理；第二，把 `serve` 和 `stay_silent` 都定义为正式输出，避免为了完成生成任务而强行出卡；第三，同时构造正向和负向 Case，并用统一 Rubric 评估相关性、价值、事实依据、表达和克制度。公开实现使用透明、无依赖的确定性规则与完全合成数据，便于读者复现和替换为自己的检索、排序或生成组件。

## 1. 问题定义与目标

### 1.1 主动卡片服务与普通推荐的区别

普通推荐主要回答“用户可能喜欢什么”；主动卡片服务还要回答“现在是否值得打扰用户”。这增加了三个前置判断：当前情景是什么、用户在此情景下可能需要什么、系统是否拥有足够可靠且可承接的事实。

如果把所有 Context 直接交给生成模型，系统容易出现四类错误：

1. **相关性错误**：Context 存在，但与此刻情景没有关系，模型仍然把它写进文案。
2. **时机错误**：内容本身有价值，但已经过期、距离过远或不适合当前天气，仍然被推送。
3. **服务错误**：有兴趣不等于现在应该出卡，系统缺少明确的沉默出口。
4. **证据错误**：文案听起来合理，却无法说明具体依据来自哪个输入事实。

本框架的目标不是最大化出卡数量，而是在可追溯事实的基础上，提升“该服务时服务、不该服务时克制”的稳定性。

### 1.2 输入与输出

输入由四类公开抽象数据组成：

| 输入类别 | 作用 | 公开版示例 |
|---|---|---|
| 用户 Context | 描述用户稳定或当前可用的特征 | `local_status`、`preference_tags` |
| 环境 Context | 描述当前时空与环境条件 | 城区、当地小时、天气 |
| Event Context | 提醒卡的事实锚点 | 主题、状态、距离、关系度、事实描述、动作 |
| POI Context | 推荐卡的候选地点特征 | ID、名称、距离、开放状态、标签、Summary 主题、卡片主题 |

统一结果包含：

- `decision`：`serve` 或 `stay_silent`；
- `need_record`：情景、潜在需求、约束、证据和置信度；
- `card`：出卡时的用户可见内容，沉默时为 `null`；
- `decision_reasons`：面向产品和算法的内部判断依据；
- `expected_decision`：Case 的预期决策，用于评测。

### 1.3 设计边界

公开框架只使用合成数据和抽象字段，不包含真实用户、真实地点、商业 API、企业内部字段、私有规则或未授权数据。公开基线强调可解释和可复现，不声称是生产级推荐模型，也不直接适用于真实用户推送。

### 2.2 模块速览

| 模块 | 解决的问题 | 产出 |
|---|---|---|
| Context 输入 | 系统知道哪些事实 | 结构化 Context |
| 情景识别 | 当前到底发生了什么 | 当前情景描述 |
| 需求翻译 | 用户此刻可能需要什么 | `need_record` |
| 候选处理 | 哪些事实或地点值得继续判断 | 候选集与证据 |
| 服务决策 | 现在该不该出卡 | `serve` / `stay_silent` |
| 内容生成 | 如何把判断转成卡片 | 用户内容和内部解释 |
| 校验评测 | 输出是否可靠、可复现 | 校验结果和评分 |

### 2.3 为什么必须分层

分层的关键不是增加流程，而是把不同类型的判断拆开：情景识别负责“发生了什么”，需求翻译负责“可能需要什么”，服务决策负责“是否值得服务”，内容生成负责“怎么表达”。如果把四个问题混成一个生成步骤，错误很难定位，也无法判断是 Context 不足、筛选不对、决策错误还是文案表达问题。

## 3. Context 到情景与需求记录

### 3.1 Context 的角色分类

一个字段在推理中的作用通常属于以下三类之一：

| 角色 | 含义 | 使用方式 |
|---|---|---|
| 事实证据 | 直接描述正在发生的事情 | 支撑情景和最终文案 |
| 关系信号 | 描述用户与事情/地点的关联 | 判断是否对用户有价值 |
| 约束条件 | 限制时间、距离、天气或可用性 | 过滤不合适内容 |

同一个字段不应被默认视为“越多越好”。例如偏好标签可以作为关系信号，但不能单独证明用户现在就要去某个地点；天气通常是约束条件，也可能影响副文案，但不能单独决定 Icon 或推荐主题。

### 3.2 需求记录的结构

公开基线中的 `need_record` 包含五个部分：

```json
{
  "situation": "晚间，用户位于星河城区，面对一个周末市集事件",
  "need": "判断周末市集是否值得在当前时机提醒",
  "constraints": [
    "事实必须在当前时间有效",
    "不使用未提供的行程或订单信息",
    "优先当前可达且距离合理的内容"
  ],
  "evidence": [
    "时间处于晚间",
    "当前天气为晴朗",
    "用户属于常驻城市",
    "事件状态为active"
  ],
  "confidence": 0.85
}
```

- `situation`：用自然语言概括当前情景，不添加输入中没有的计划。
- `need`：把情景转成下一步需要判断或满足的潜在需求。
- `constraints`：明确事实有效性、距离、天气和数据边界。
- `evidence`：列出真正支撑判断的输入字段或字段组合。
- `confidence`：表示当前需求翻译的可信程度，不等同于最终出卡概率。

### 3.3 需求记录如何发挥作用

需求记录是后续模块之间的中间契约，而不是面向用户的文案。候选检索使用其中的空间、时间和主题约束；排序使用其中的关系信号和证据；服务判断检查候选是否满足记录中的关键约束；内容生成只能使用记录中有证据支撑的需求，不能在最后一步凭空补充用户计划、订单或隐含意图。

> **例子：从 Context 到需求记录**
>
> 输入：用户处于常驻城市，当前上午，天气晴朗，附近 1.3 公里有一个状态为 active 的周末市集事件，关系度为 0.72。
>
> 翻译：情景是“上午、附近、当前有效的周末市集”；需求是“判断是否值得在此刻提醒”；约束是“事件必须有效、距离合理、不得依赖不存在的行程”；证据来自时间、天气、常驻状态、事件状态、距离和关系度。
>
> 作用：事件路径据此决定是否出卡；如果事件状态变为 inactive 或距离超过边界，后续服务判断可以沉默，而不是继续生成原来的文案。

## 4. 事件提醒卡：从 Event 到卡片

### 4.1 事件卡完整流程图

```text
┌──────────────────────┐
│ 1. 输入合成 Context   │
│ 用户 + 环境 + Event   │
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ 2. 识别当前情景       │
│ 时间/天气/位置/关系   │
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ 3. 生成 need_record   │
│ 情景/需求/约束/证据    │
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ 4. Event 服务判断     │
│ 有效性/距离/关系/时机  │
└───────┬────────┬─────┘
        │不满足   │满足
        ▼        ▼
┌────────────┐  ┌────────────────────────┐
│ stay_silent│  │ 5. 生成事件卡内容       │
│ 记录沉默原因│  │ 主/副文案 + Action + Icon│
└────────────┘  └───────────┬────────────┘
                             ▼
                  ┌────────────────────────┐
                  │ 6. 事实与表达校验       │
                  │ 结构/字数/证据/决策一致 │
                  └────────────────────────┘
```

### 4.2 输入要求与硬边界

事件卡以一个 Event 作为事实锚点。Event 至少需要有主题、当前状态、距离、与用户的关系度、事实描述和可执行动作。公开版禁止依赖未提供的行程、订单、导航目的地或足迹；地点排行榜类内容不作为事件事实输入。

`TOPLIST_POI` 这类地点榜单类型不进入事件提醒卡路径，否则会把“发现地点”和“提醒一个当前事件”混成同一类服务，导致事件卡与 POI 卡重复。

### 4.3 服务判断逻辑

公开基线采用透明规则：

1. Event 状态必须是当前有效状态 `active`；
2. 距离必须在公开版可达边界内（基线为不超过 8 公里）；
3. 关系度必须达到基线门槛（基线为不低于 0.6）；
4. 需求记录中的关键约束不能被当前天气、时段或事实状态明显违背。

任一关键门槛不满足，输出 `stay_silent`，并在 `decision_reasons` 记录沉默原因。门槛是可替换的基线参数，不应被误解为所有产品都必须使用的固定数值。

> **例子：事件卡为什么沉默**
>
> Event 主题为“户外演出”，状态为 `active`，但距离为 12.4 公里。即使用户有“户外”偏好，距离已超出当前服务边界，结果应为 `stay_silent`，原因是“事件距离超过公开版可达范围”。系统不能因为有偏好就强行生成提醒。

### 4.4 事件卡内容生成

事件卡的用户可见内容包括主文案、副文案和一个 Action；同时输出一个 Icon 标签和内部判断依据。

**主文案**表达“与用户的关系 + 当前价值 + 具体事情”，最多 16 个中文字符，结尾不使用句号或其他标点。主文案不能只是把 Event 名称原样复述，也不能固定追加“可以看详情”“可以看路线”等机械尾句。

**副文案**承接结构化事实，优先使用 Event 的事实描述、时间、地点等可靠字段。若 Action 已经明确指向某个 POI 详情，副文案不再重复 ETA 类信息；副文案不是营销口号，也不应添加输入中不存在的事实。

**Action**必须是用户视角的可执行动作，文案长度为 2～4 个中文字符，避免信息标签化。示例包括“导航”“找加油站”“去看看”“设提醒”。当 Action 跳转到明确 POI 时，输出对应的 POI 名称供后续链路使用。

**Icon**主要根据事件类型和关联 POI 类型选择，天气只能作为辅助判断，不能成为主要依据。标签同时输出英文和中文，例如 `{"en":"market","zh":"市集"}`。

> **例子：事件卡生成**
>
> Event 事实：“今天 10:00-18:00，星河城区有周末市集”，用户为常驻城市用户，距离 1.3 公里，状态 active。
>
> 主文案：“周末有去处 正好离你近”
>
> 副文案：“今天10:00-18:00，星河城区有周末市集”
>
> Action：“去看看”
>
> Icon：`market / 市集`

```text
┌─────────────────────────────┐

       ┌───────┴────────┐
       │无合适候选       │有合适候选
       ▼                ▼
┌────────────┐  ┌─────────────────────────────┐
│ stay_silent│  │ 7. 生成 POI 卡               │

└────────────┘  └──────────────┬──────────────┘
                               ▼
                    ┌─────────────────────────┐
                    │ 8. 校验与评测            │
                    │ 来源/数量/主题/事实/表达  │
                    └─────────────────────────┘
```

### 5.2 先形成需求，再看 POI

POI 卡不是把“离用户近的地点”直接排序后展示。第一步必须从用户和环境 Context 形成一个潜在需求与约束记录，例如“晚间、天气适宜、用户在常驻城市，希望低决策成本地找到附近可去的去处”。

这份记录的作用是将模糊的情景翻译为可执行的搜索条件：距离边界决定候选范围，天气决定室内/低暴露约束，用户偏好和 POI Summary 决定主题匹配，时段决定地点是否仍有行动价值。这样做可以避免“先看 POI 再找理由”，也能让推荐理由解释为什么这些地点满足当前需求。

> **例子：需求翻译如何约束搜索**
>
> 输入：用户偏好“户外、轻松活动”，当前下午，天气晴朗，位于星河城区。
>
> 需求记录：寻找附近、当前可去、决策成本低的户外活动；约束是地点要开放、距离合理；证据是下午、晴朗、用户偏好。
>
> 后续：先排除 7 公里外或已关闭地点，再在剩余候选中优先保留 Summary 主题与“轻松活动”一致的地点。一个标签命中但 Summary 明确是“高强度竞技”的地点，可能需要降权或淘汰。

### 5.3 候选池建立：距离是第一道边界

候选池的第一原则是“此刻可达”。公开基线先检查距离和开放状态，距离超过 5 公里或状态不是 `open` 的地点不进入有效候选。这个边界是可动态调整的参数，真实系统可以按城市、交通方式、时间段和用户状态变化，但顺序不变：先保证空间可达，再比较兴趣匹配。

候选池不是最终推荐结果。它保留多个候选，供后续结合 Summary、标签、用户关系和主题一致性进行精排。这样可以避免只因距离最近就直接推荐一个与用户情景无关的地点。

### 5.4 粗排：Summary 和结构化字段同时生效

粗排同时使用两路信息：

- **结构化字段**提供稳定事实，如距离、开放状态、兴趣标签、消费区间和热度等；
- **Summary**提供对地点特色和用户关系的概括，帮助识别“这个地点为什么适合当前用户”。

公开基线中，距离贡献 0.45，用户标签重合贡献 0.35，Summary 主题命中贡献 0.20。权重只是透明示例，重点是 Summary 在粗排阶段就参与候选保留，而不是等到最后生成理由时才补充。

> **例子：Summary 让候选被淘汰**
>
> 两个地点距离都为 1.5 公里，也都带有“户外”标签。地点 A 的 Summary 主题是“亲子轻松活动”，地点 B 的 Summary 主题是“高强度攀岩”。如果当前用户只有“轻松活动”偏好，A 的 Summary 与需求一致，B 虽然标签相同，也应被降权；这不是只看一个标签能做出的判断。

### 5.5 精排与 1～3 个 POI 的数量决策

精排在有效候选中综合距离、标签重合、Summary 主题匹配和主题一致性，最终选择 1～3 个 POI。一个 POI 适合需求非常集中时使用；两个或三个 POI 适合用户有一个明确主题、但存在多个可比较选择时使用。多个 POI 不应只是“凑数量”，最好覆盖同一个可解释主题。

公开基线按分数降序选择最多三个候选，并在最高分低于 0.42 时保持沉默。真实系统可替换评分函数，但必须保留三条约束：最终 POI 必须来自候选池、数量不超过 3、没有足够匹配度时不出卡。

### 5.6 POI 卡内容生成

**主题**是内部字段，用于说明这组地点为什么被放在一起，不直接展示给用户。

**主文案**表达“这个用户此刻为什么值得去 + 具体去做什么”，控制在 12～16 个中文字符，最多不超过 16 个字符；中间允许有空格，结尾不使用标点。文案不能使用冒犯用户的“少花点”等暗示，也不能对同一类地点反复套用固定句式。

**副文案**提供一行辅助事实，不使用 ETA 类信息作为 POI 卡公共副文案的默认内容，因为具体 ETA 会在单个 POI 点位上承接。副文案必须来源于 POI 的结构化字段或 Summary，例如地点特色、适合人群、主题组合或可验证的营业信息；如果没有可靠事实，可以不出副文案。

**推荐理由**是内部字段，不是 C 端文案。它应简要说明距离、用户偏好命中、Summary 主题、结构化特征和主题一致性，避免写成一大段无法复核的解释。

**图片标签**按“二级 Tag > 一级分类”选择。如果多个 POI 无法共享合理的二级 Tag，则尝试使用共同一级分类；一级分类也不合适时，输出“未找到合适标签”的标识，不使用全局通用兜底替代真实匹配。

> **例子：POI 卡生成**
>
> 用户在常驻城市，当前下午，偏好“户外、轻松活动”；候选中有三个地点均在 3 公里内、处于开放状态，Summary 分别强调“城市绿地散步”“轻松骑行”“亲子户外”。
>
> 内部主题：“附近轻松户外”
>
> 最终 POI：三个地点的 ID 和名称
>
> 主文案：“附近有几处轻松户外去处”
>
> 副文案：“3公里内，适合下午放松走走”
>
> 推荐理由：距离均在候选边界内；命中“户外/轻松活动”偏好；Summary 都指向低强度户外；三个地点主题一致，适合并列展示。

## 6. 服务决策：出卡与沉默都是结果

### 6.1 统一决策契约

服务决策位于候选处理和内容生成之间。它只回答一个问题：在当前情景和事实条件下，系统是否有足够依据提供服务。

```text
满足事实有效性？
      │否 → stay_silent
      │是
      ▼
满足用户关系与当前价值？
      │否 → stay_silent
      │是
      ▼
满足时间、距离、可用性约束？
      │否 → stay_silent
      │是
      ▼
存在可承接的事件或 POI？
      │否 → stay_silent
      │是
      ▼
serve → 进入卡片生成
```

### 6.2 两类卡片的判断差异

| 判断对象 | 事件提醒卡 | POI 推荐卡 |
|---|---|---|
| 事实锚点 | 一个当前有效 Event | 候选 POI 集合 |
| 首要问题 | 这件事现在值得提醒吗 | 现在有哪些地点值得推荐 |
| 关键过滤 | 状态、距离、关系度、时机 | 距离、开放状态、需求匹配 |
| 沉默原因 | 事件过期、太远、关系不足 | 无合适候选、距离过远、地点不可用 |
| 最终对象 | 一个事件 + 一个 Action | 1～3 个 POI |

### 6.3 为什么负向 Case 必须存在

只构造“应该出卡”的 Case，会让系统看起来总是有答案，却无法判断它是否会过度服务。负向 Case 用来测试：事件过期时是否沉默、地点都太远时是否沉默、关系不足时是否沉默、候选池为空时是否沉默。负向 Case 不是异常数据，而是主动服务系统的正常输出空间。

> **例子：负向 POI Case**
>
> 用户偏好“轻松活动”，但候选地点全部距离超过边界或状态为 closed。即使偏好与地点标签有重合，也应输出 `stay_silent`，并说明“没有候选地点同时满足距离、可用性和关系条件”。

## 7. 卡片内容与输出契约

### 7.1 事件提醒卡输出

```json
{
  "card_type": "event",
  "decision": "serve",
  "card": {
    "main_copy": "周末有去处 正好离你近",
    "sub_copy": "今天10:00-18:00，星河城区有周末市集",
    "action": "去看看",
    "icon_tag": {"en": "market", "zh": "市集"}
  }
}
```

### 7.2 POI 推荐卡输出

```json
{
  "card_type": "poi",
  "decision": "serve",
  "theme": "附近轻松户外",
  "selected_pois": [
    {"poi_id": "poi_s001", "name": "星河绿地"},
    {"poi_id": "poi_s002", "name": "河畔骑行道"}
  ],
  "card": {
    "main_copy": "附近有几处轻松户外去处",
    "sub_copy": "3公里内，适合下午放松走走"
  },
  "recommendation_reason": "距离、开放状态和用户偏好均满足；Summary 共同指向低强度户外主题"
}
```

### 7.3 用户内容与内部解释分离

主文案和副文案服务于用户理解和行动；主题、推荐理由、证据和决策原因服务于产品、算法和评测。两者不能混写：内部理由可以稍微详细，但不应直接展示给用户；用户文案必须短、自然、有事实依据。

## 8. 测评数据集构造方法

### 8.1 Case 的最小组成

每条 Case 至少包含：

| 字段 | 说明 |
|---|---|
| `case_id` | 唯一标识 |
| `card_type` | `event` 或 `poi` |
| `context` | 用户、环境、事件或候选 POI |
| `expected_decision` | 预期 `serve` 或 `stay_silent` |
| `scenario_label` | 合成数据的情景标签，用于分布检查 |

运行后再生成 `need_record`、实际 `decision`、卡片和理由，避免把模型结果与输入 Case 混为一谈。

### 8.2 正向与负向数据

正向 Case 验证该出卡时是否能出对：事实有效、关系成立、时机和距离合理、存在可承接内容。负向 Case 验证系统是否克制：事实失效、距离过远、关系不足、候选不可用或没有足够匹配的地点时应保持沉默。

数据集不追求所有排列组合，而是覆盖能改变服务决策或内容选择的关键变化：不同时间段、天气、常驻/到访状态、偏好组合、事件类型、POI 主题、候选数量和距离分布。特殊日期可以出现，也必须保留大量没有特殊日期的普通日常 Case，避免数据分布过于理想化。

### 8.3 生产后的自查

每批数据生成后，先做自动和人工抽样检查：

1. 结构检查：字段存在、类型正确、JSON 可解析。
2. 来源检查：文案和理由是否能在 Context、Event 或 POI 字段中找到依据。
3. 决策检查：预期决策与实际决策是否一致。
4. 边界检查：事件是否误用禁止类型，POI 是否超出数量和距离约束。
5. 表达检查：主文案长度、结尾标点、Action 形式、副文案事实性。
6. 分布检查：是否出现模板化、某一特殊日期过多、某类天气或主题垄断。

## 9. Taste 与 Rubric

### 9.1 Taste 的作用

Taste 是“什么样的服务才值得被认为是好服务”的产品判断，不等同于字段规则。它约束输出应该有真实关系、即时价值、事实依据、自然表达和适度克制。

### 9.2 Rubric 的作用

Rubric 将 Taste 转成可执行的 0～2 分评测标准。每个维度同时包含：评估定义、事件提醒卡细则、POI 推荐卡细则和参考案例。评分时先判断该分数的关键条件是否满足，再结合整体表现给出结果；不是机械地要求所有描述性条件逐字同时出现。

### 9.3 统一评测维度

公开版使用五个维度：

| 维度 | 评估核心 |
|---|---|
| D1 相关性与情景贴合 | 是否回应当前情景、用户关系和此刻需求 |
| D2 用户价值 | 是否提供清晰、具体、值得采取行动的价值 |
| D3 事实依据与可信度 | 是否能追溯到输入事实，是否避免虚构 |
| D4 表达自然度与可读性 | 是否简洁、自然、符合卡片语气和长度约束 |
| D5 服务克制度与选择质量 | 是否该出才出、该沉默时沉默，候选是否合理 |

事件卡重点看 Event 是否值得提醒、Action 是否可执行、Icon 是否匹配；POI 卡重点看候选是否适合、1～3 个 POI 是否主题一致、Summary 和结构化特征是否真正参与选择。

### 9.4 评测结果的解释

评测不只给总分，还要保留每个维度的得分和证据。例如一张卡片可能 D1、D2 较高，但 D3 较低，说明情景和价值判断合理，却使用了无法追溯的副文案；也可能 D1、D3 合格，但 D4 较低，说明事实正确、场景相关，却写得机械。这种拆分比单一“好/不好”更有助于迭代。

## 10. Demo 与可复现实现

公开 Demo 是一个不连接商业 API 的静态浏览器应用。用户可以：

1. 选择事件提醒卡或 POI 推荐卡；
2. 选择一个公开合成 Case；
3. 调整当地时间、天气和偏好标签；
4. 点击“运行 Case”；
5. 依次查看输入 Context、情景与潜在需求、候选、服务决策、最终卡片和内部判断依据。

Demo 的目的不是模拟真实地图检索，而是让中间推理契约可见：读者可以观察同一个 Case 在时间、天气或偏好变化后，需求记录、候选和服务决策如何变化。运行按钮会显示最近运行的 Case 和时间，便于确认交互已经生效。

公开代码包含：

- `pipeline/engine.py`：确定性基线逻辑；
- `schemas/`：Context 和卡片输出结构；
- `data/public_cases.jsonl`：合成正负向 Case；
- `validators/validate_outputs.py`：结构和公开边界检查；
- `hf_space/index.html`：无需服务端依赖的静态 Demo。

### 10.1 报告方法与公开基线的对应关系

本文描述的是可以替换和扩展的完整方法，当前仓库提供的是一个透明、确定性的最小基线。两者需要明确区分：基线中的 Summary 使用 `summary_theme` 的可解释命中作为示例信号，并不等于已经实现了完整的文本语义匹配；基线的 POI 精排直接按分数和距离取前 3 个候选，还没有独立的主题一致性过滤器；天气和时间在当前 POI 基线中主要影响 `need_record`，没有直接进入 POI 分数；事件基线检查 `status`、距离和关系度，不解析 Event 的详细时间窗口。

同样，验证器主要检查 JSON 可解析性、核心枚举、预期决策一致性、沉默时卡片为空、重复 ID 和少量公开边界禁词，不会自动证明语义相关性、证据充分性、Summary 质量或文案自然度。这些部分需要人工或模型 Rubric 评审。输出 Schema 目前声明核心字段，`source`、`expected_decision`、`candidate_pool`、`selected_pois` 等是公开结果中的扩展字段，后续可在 Schema 版本升级时正式纳入。

这样的取舍是有意的：先用小而透明的实现把“需求翻译—候选处理—服务决策—卡片生成—评测”完整跑通，再逐步替换单个模块，而不是用一个不可解释的黑盒模型掩盖流程缺口。

## 11. 局限、风险与后续工作

### 11.1 当前局限

第一，公开数据为合成数据，不能代表真实用户分布、真实地点质量或线上点击效果。第二，公开基线使用透明规则，权重和门槛用于展示流程，并非经过大规模线上校准的生产参数。第三，当前 Rubric 需要人工或模型评审来完成语义判断，自动校验只能覆盖结构和部分硬约束。

### 11.2 使用风险与解法

如果直接把公开基线接入真实用户服务，可能产生隐私、许可、错误推荐和过度打扰风险。正确做法是重新完成数据授权、隐私保护、业务安全、真实分布校准和线上效果评估；不能把合成字段替换成真实字段后直接上线。

### 11.3 可扩展方向

后续可以在不改变总体顺序的前提下替换模块：用真实检索系统替换候选池生成，用学习排序替换透明评分，用语言模型替换内容生成，用自动评测器补充 Rubric 执行，并将用户反馈接入数据集迭代。无论如何扩展，都应保留“先形成情景和需求、再处理候选、再做服务决策、最后生成内容”的可审计链路。

---

## 12. 结论

Agent 卡片服务的核心不是让模型写出更多文案，而是让系统在复杂 Context 中做出可解释的服务判断。本文框架用需求记录把 Context 和卡片之间的推理显式化，用 `serve` / `stay_silent` 统一表达服务与克制，用事件卡和 POI 卡两条不同路径承接不同事实结构，并通过正向、负向 Case 和 Rubric 把结果变成可重复评测的对象。

这种方法的可迁移性来自流程契约，而不是某个城市、某个地点或某组固定规则：只要新的 Agent 服务也需要理解当前情景、判断是否值得服务、选择可承接内容并生成用户卡片，就可以复用同一套分层思路，再替换具体 Context、候选和内容规则。
