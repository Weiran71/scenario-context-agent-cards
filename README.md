# 基于用户情景和 Context 的 Agent 卡片服务生成框架

这是一个完全独立重建的公开研究原型，用合成数据演示 Agent 如何把多源 Context 转化为两类主动服务卡片：事件提醒卡和 POI 推荐卡。

本项目不包含真实用户数据、真实地图数据、商业产品字段、内部业务规则或任何企业内部文档。它不代表任何商业导航或推荐产品的官方实现。

## 项目主链路

```text
Context
  ↓
当前情景识别
  ↓
潜在需求与约束翻译
  ↓
服务机会判断
  ↓
候选检索、过滤与排序
  ↓
卡片生成
  ↓
正向 / 负向评测
```

事件提醒卡回答“此刻是否值得提醒”；POI 推荐卡回答“此刻哪些地点值得推荐”。两类卡共享 Context 和评测底座，但有不同的决策契约。

## 项目要解决什么问题

传统推荐通常从“用户喜欢什么”出发，直接返回内容；主动服务还要解决一个更难的问题：**当前这一刻，系统是否有足够理由主动打扰用户**。

如果把大量用户、环境、时间、事件和地点字段直接交给生成模型，常见问题包括：

- Context 很多，但无法判断哪些信息真正相关；
- 推荐结果和当前时间、位置或用户关系脱节；
- 有合适内容却没有先判断是否值得服务；
- 正向案例看起来合理，但负向情景仍然强行出卡；
- 文案说得通，却无法追溯依据来自哪个事实。

本项目将卡片生成拆成可观察、可复现的中间步骤，让系统先理解情景和潜在需求，再决定是否服务，最后才生成用户可见内容。

## 对用户的价值

对终端用户，目标不是增加信息量，而是减少在当前情景下的决策成本：

- 在确实有价值的时机得到一条简洁提醒；
- 获得与此刻位置、时间和个人偏好匹配的附近去处；
- 看到的是有事实依据的服务，而不是脱离当下的泛兴趣推荐；
- 在不合适的时机不被打扰。

对 Agent 产品和算法开发者，项目提供一套可以复用的中间契约、数据结构和评测方法，用于定位“为什么出卡”“为什么不出卡”以及“卡片是否真的回应了当前情景”。

## 核心亮点

### 1. Context 先翻译成潜在需求与约束

系统不从 Context 直接跳到文案，而是先生成 `need_record`。它记录当前情景、潜在需求、空间和时间约束、证据以及置信度。这个记录既是候选检索的输入，也是后续排序和解释的依据。

### 2. 先判断是否值得服务，再生成卡片

`serve` 和 `stay_silent` 都是合法输出。只有事实有效、与用户有关系、时机合适、价值足够且存在可承接内容时才出卡；否则保留沉默，避免为了完成生成任务而主动打扰。

### 3. 两类卡片使用不同的决策契约

事件提醒卡以当前有效的 Event 为事实锚点，判断“现在是否应该提醒”；POI 推荐卡以用户此刻的空间和情景为起点，判断“现在推荐哪些地点”。两者共用 Context、校验和评测底座，但不共用一套简单模板。

### 4. 正向和负向案例同时构建

正向案例验证“该出时能否出对”，负向案例验证“该沉默时能否克制”。这使评测目标从文案质量扩展到服务判断质量。

## 事件提醒卡生产流程

```text
合成 Context + 当前有效 Event
              ↓
情景识别：时间、天气、位置、用户关系
              ↓
需求记录：是否值得在此刻提醒
              ↓
事实与服务门槛检查
              ├── 不满足 → stay_silent
              └── 满足   → 进入卡片生成
                              ↓
                    主文案 + 副文案 + Action + Icon
                              ↓
                    结构校验、证据校验、结果评测
```

### 步骤说明

1. **读取 Context 和 Event**：输入用户偏好、常驻/到访状态、时间、天气、城区以及一个合成 Event。
2. **识别当前情景**：将时间段、天气、用户与地点关系转化为情景描述，例如“晚间、到访城市、附近有当前有效的音乐活动”。
3. **生成需求记录**：明确这条 Event 可能为用户带来的价值、适用的时间和空间约束，以及支撑判断的字段证据。
4. **执行服务判断**：检查 Event 是否有效、距离是否合理、与用户是否有关系、当前是否仍有行动价值。任一关键条件不满足，就输出 `stay_silent`。
5. **生成卡片内容**：满足条件时生成用户可见的主文案和副文案，同时给出一个可执行 Action、一个图标标签和内部判断依据。
6. **校验与评测**：检查输出结构、决策与 Case 标注是否一致、卡片内容是否有输入证据支撑，并保留负向案例的沉默原因。

## POI 推荐卡生产流程

```text
合成 Context + POI 候选池
              ↓
情景识别：此刻的时间、位置、天气和用户特征
              ↓
潜在需求与约束翻译
              ↓
距离和可用性边界
              ↓
结构化标签 + Summary 双路匹配
              ↓
候选过滤与排序
              ├── 无合适候选 → stay_silent
              └── 有合适候选 → 选择 1～3 个共同主题 POI
                                      ↓
                         主题 + 主文案 + 副文案
                                      ↓
                         推荐依据、校验与评测
```

### 步骤说明

1. **读取 Context 和候选池**：输入用户偏好、常驻/到访状态、当前位置所在城区、时间、天气和多个合成 POI。
2. **生成潜在需求与约束**：把 Context 翻译成“用户现在可能需要什么、只能接受什么、哪些内容应排除”的结构化记录。
3. **建立候选边界**：距离是第一层约束，同时检查地点是否处于可用状态。距离过远或当前不可用的地点直接淘汰。
4. **双路匹配**：同时使用 POI 的结构化标签和 Summary 主题。结构化字段提供稳定事实，Summary 提供对地点特征的概括，两者共同影响候选保留、排序和最终理由。
5. **候选排序与数量决策**：在候选池内综合距离、用户偏好、Summary 匹配和共同主题，最终选择 1～3 个 POI；多个 POI 需要具备可解释的主题一致性。
6. **服务判断**：如果没有候选同时满足距离、可用性和用户关系条件，输出 `stay_silent`，不为了凑数量而推荐。
7. **生成卡片**：有合适候选时，生成内部主题、用户可见主文案、副文案以及说明为什么选择这些 POI 的推荐理由。
8. **校验与评测**：检查最终 POI 是否来自候选池、主题是否一致、文案是否有字段和 Summary 依据、负向 Case 是否正确沉默。

## 统一输出契约

两类卡片都输出以下通用结构：

| 字段 | 作用 |
|---|---|
| `case_id` | Case 唯一标识 |
| `card_type` | `event` 或 `poi` |
| `decision` | `serve` 或 `stay_silent` |
| `need_record` | 当前情景、潜在需求、约束和证据 |
| `card` | 出卡时的用户可见内容；沉默时为 `null` |
| `decision_reasons` | 内部可复核的判断依据 |
| `source` | 数据来源类型，公开版为 `synthetic` |

事件卡在 `card` 中增加 Action 和 Icon；POI 卡增加主题、最终 POI 和副文案。完整字段定义见 [`schemas/`](schemas/)。

## 评测方式

公开基线同时评估“出不出”和“出了以后好不好”：

- **决策一致性**：实际 `serve` / `stay_silent` 是否符合 Case 标注；
- **情景相关性**：结果是否回应当前时间、地点、天气和用户关系；
- **证据充分性**：需求记录、推荐理由和卡片内容能否追溯到输入字段；
- **服务克制度**：负向情景是否避免强行出卡；
- **表达可用性**：主文案简洁，副文案提供事实补充，内部理由便于复核。

自动校验负责结构和硬约束；语义质量仍可在此基础上接入人工或模型评审。当前公开样例是研究原型，不代表经过大规模人工标注的 Gold Benchmark。

## 当前公开版包含

- 两类卡片的抽象生产方法；
- 公开版 JSON Schema；
- 完全合成的用户、环境、事件和 POI 数据；
- 事件提醒卡和 POI 推荐卡的多个正向 / 负向 Case；
- 不依赖商业 API 的可运行基线；
- 结构与结果校验器；
- 评测字段和负向抑制示例。

## 快速运行

项目只依赖 Python 3 标准库：

```bash
python3 pipeline/run_examples.py
python3 validators/validate_outputs.py examples/generated_outputs.jsonl
```

运行后会生成 `examples/generated_outputs.jsonl`，并输出事件提醒卡和 POI 推荐卡各多个 Case 的结果。

## 公开边界

所有数据均为合成数据，地点名称、事件名称、ID、画像和环境值均为示例用途。不要将内部数据替换字段名后直接放入本仓库；如需对外发布，还应另行完成知识产权、隐私和数据许可审查。

## 当前限制与后续扩展

- 当前基线使用透明规则，不依赖商业地图 API 或私有模型；
- 当前数据规模用于验证流程闭环，不代表跨城市、跨人群的泛化能力；
- 当前事件和 POI 都是公开版合成世界，不能直接解释为现实世界服务结果；
- 后续可以增加开放许可地理数据、更多情景、模型适配器、交互式 Demo 和技术报告。

如果要把本项目用于真实产品或真实用户服务，需要重新完成数据授权、隐私保护、业务安全和效果评估，不能直接将公开基线接入线上。
